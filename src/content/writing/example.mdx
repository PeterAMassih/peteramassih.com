Reading code well is mostly about *not* reading code. The first pass is a quick scan: directory structure, top-level exports, the README, the entrypoint. You're trying to build a map, not a transcript.

Once the map is rough, pick one user-facing behavior and trace it end-to-end. The narrower the slice, the faster the loop. Don't try to understand everything — pick one path through the codebase and follow it.

## A small detour into complexity

When people argue about whether to optimize a hot path, the conversation usually centers on asymptotic complexity. That's the wrong question for small inputs.

An $O(n \log n)$ algorithm with a 200ns constant beats an $O(n)$ algorithm with a 4μs constant for any realistic $n$:

$$
T_1(n) = c_1 \cdot n \log n \qquad T_2(n) = c_2 \cdot n
$$

The crossover happens at $n = 2^{c_2 / c_1}$. For the numbers above, that's somewhere in the millions. If your $n$ is usually a few hundred, the "slower" algorithm wins every time.

## A snippet I keep coming back to

A reading-aid for unfamiliar codebases — print the path a request takes through the call graph:

```ts
function trace<T extends (...args: unknown[]) => unknown>(name: string, fn: T): T {
  return ((...args) => {
    console.log(`-> ${name}`);
    const result = fn(...args);
    console.log(`<- ${name}`);
    return result;
  }) as T;
}
```

Wrap a few suspicious functions, run the app, watch the trace. The shape of the log tells you the call structure without having to mentally simulate it.

Tiny, ugly, useful. Delete it after.
